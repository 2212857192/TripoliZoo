# الدليل الشامل والمفصّل: العملية الكاملة لنظام خريطة حديقة الحيوان التفاعلية

> هذا الملف **مرجع واحد متكامل** يشرح كل خطوة من بداية النظام حتى نهايته — من لحظة وجود ملف بيانات خام (GeoJSON) حتى لحظة وقوف الزائر فعلياً أمام قفص الأسد بعد إتباع المسار، ثم كيف تُدار كل هذه البيانات من لوحة تحكم لاحقاً. الهدف أن يقرأه شخص بلا أي خلفية سابقة عن المشروع ويخرج بفهم كامل لكل قطعة وكيف ترتبط بالأخرى.

## 1. الصورة الكبيرة: ما هي "الخريطة" فعلياً من الناحية التقنية؟

من ناحية الزائر: صورة جميلة يتجوّل فيها ويشوف مساره.
من ناحية البرنامج: **الخريطة هي 3 أشياء منفصلة تماماً تجتمع بصرياً فقط عند العرض:**

1. **صورة واحدة ثابتة (Raster Image)**: ملف PNG بحجم 4516×3374 بكسل — مجرد رسم، لا يحتوي أي "ذكاء"، فقط ألوان وأشكال.
2. **شبكة رياضية (Graph) من نقاط وخطوط**: 122 نقطة (Nodes) تمثل تقاطعات/نقاط على الممرات، و157 خط (Edges) يربط بينها، كل خط له مسافة حقيقية محسوبة. هذه الشبكة هي "العقل" الذي يفهم البرنامج عبره كيف يمشي شخص من نقطة لأخرى.
3. **قائمة معالم (Locations)**: 44 نقطة اهتمام (حيوانات، مطاعم، بوابات...) كل واحدة مرتبطة بأقرب نقطة من الشبكة الرياضية.

**القاعدة الذهبية لكل ما سيأتي بهذا الملف**: كل هذه الثلاثة (الصورة، الشبكة، المعالم) تتحدث "لغة" واحدة هي **بكسل الصورة الأصلية (x, y)**. أي عملية حسابية بالنظام — تحديد موقع، حساب مسار، رسم خط — تتم بهذه اللغة فقط، ولا تتحول لأي نظام آخر (شاشة، نسبة، GPS) إلا في طرفي العملية: عند استقبال إدخال من الزائر (لمسة/GPS)، وعند الرسم النهائي على الشاشة. أي خلط بين الأنظمة في المنتصف هو سبب 90% من المشاكل (كما حدث فعلياً بمشكلة محور Y التي اكتشفناها سابقاً بهذا المشروع).

## 2. بنية بيانات الخريطة (ملف GeoJSON) — شرح كل حقل

الملف الحالي (`Zoo_Routing_Ready.geojson`) هو `FeatureCollection` قياسي، فيه 323 عنصر (`feature`)، كل واحد من 3 أنواع تُحدَّد بحقل `properties.entity`:

### 2.1 نوع `map_path_node` (122 عنصر) — نقطة على الشبكة
```json
{
  "properties": {
    "entity": "map_path_node",
    "node_key": "N001",          // معرّف فريد لهذي العقدة، يُستخدم بكل مكان آخر للإشارة لها
    "node_kind": "manual",        // "manual" = رُسمت يدوياً، "auto_endpoint" = أنشأتها الأداة تلقائياً كنقطة نهاية
    "is_active": true              // لو false: هذي العقدة معطّلة، تُستثنى من حساب أي مسار
  },
  "geometry": { "type": "Point", "coordinates": [x, y] }   // بكسل على الصورة
}
```

### 2.2 نوع `map_path_edge` (157 عنصر) — خط يربط بين عقدتين
```json
{
  "properties": {
    "entity": "map_path_edge",
    "edge_key": "E001",
    "from_node_key": "N121",         // العقدة الأولى
    "to_node_key": "N115",            // العقدة الثانية
    "is_bidirectional": true,          // هل يمكن المرور بالاتجاهين؟ (دائماً true عملياً لممرات مشاة عادية)
    "is_accessible": true,              // مناسب لكرسي متحرك؟ (يُستخدم لتصفية المسار لاحقاً)
    "is_active": true,                   // لو false: ممر مغلق مؤقتاً (صيانة) — يُستثنى من الحساب لكن يبقى محفوظاً بالبيانات
    "distance_units": 434.75              // المسافة الفعلية بالبكسل، محسوبة من طول الخط الحقيقي (وليس الخط المستقيم بين العقدتين!)
  },
  "geometry": {
    "type": "LineString",
    "coordinates": [ [x1,y1], [x2,y2], [x3,y3], ... ]   // كل النقاط التي يتبعها الممشى الحقيقي بانحناءاته
  }
}
```
**نقطة بالغة الأهمية**: حقل `geometry.coordinates` هنا ليس فقط نقطتين (بداية ونهاية)! بل قائمة كاملة من النقاط الوسيطة التي تتبع شكل الممشى الحقيقي على الأرض (منحنياً حول مبنى، ملتفاً حول بحيرة...). هذا ما يفرّق بين خريطة "ذكية تتبع الواقع" وخريطة "خطوط مستقيمة وهمية تقطع فوق المباني" — وهذا تحديداً ما تحققنا منه سابقاً بفحص الملف.

### 2.3 نوع `map_location` (44 عنصر) — معلم/نقطة اهتمام
```json
{
  "properties": {
    "entity": "map_location",
    "location_key": "L012",
    "name": "الاسد الإفريقي",
    "location_type": "animal",            // animal / restaurant / entrance / theater / security / lake ...
    "description": null,                    // نص تفصيلي يظهر للزائر عند الضغط (يُملأ من لوحة التحكم)
    "nearest_node_key": "N047",              // أقرب عقدة بالشبكة لهذا الموقع (محسوبة مسبقاً عند الرسم)
    "link_distance_units": 0.81,              // المسافة بين الموقع ونقطة nearest_node (للتحقق من معقولية الربط)
    "is_active": true
  },
  "geometry": { "type": "Point", "coordinates": [x, y] }
}
```

### 2.4 ميتاداتا الملف (Header)
```json
"metadata": {
  "image_width": 4516,
  "image_height": 3374,
  "coordinate_system": "image-pixel-xy",
  "node_count": 122, "location_count": 44, "edge_count": 157
}
```
هذا القسم يُقرأ أول شيء عند تحميل أي ملف خريطة، للتأكد من تطابق أبعاد الصورة المرفوعة مع البيانات.

## 3. تحميل الخريطة في تطبيق الزائر (الطبقات الثلاث)

عند فتح شاشة الخريطة بالتطبيق، يحدث هذا الترتيب بالضبط:

**الخطوة 1**: التطبيق يطلب من الخادم `GET /api/map/active` (تفصيل كامل بالقسم 10) ويحصل على: رابط صورة PNG + كل العقد + كل الحواف + كل المواقع، دفعة واحدة.

**الخطوة 2**: تحميل الصورة وعرضها داخل ويدجت `InteractiveViewer` (يدعم التكبير بإصبعين Pinch-to-Zoom، والتحريك بالسحب). هذه **الطبقة الأولى (الأسفل)**.

**الخطوة 3**: بناء **الطبقة الثالثة (الأعلى)**: لكل عنصر بقائمة `locations`، يُرسم أيقونة (Icon/Marker) في موضعه `(x, y)` المحوَّل لموضع نسبي على الصورة المعروضة حالياً (حسب مستوى التكبير). هذه الأيقونات قابلة للضغط.

**الخطوة 4**: تجهيز (وليس عرض بعد) **الطبقة الثانية**: بناء كلاس `LocationProvider` بالذاكرة، جاهز لاستقبال موقع الزائر لاحقاً (يدوياً أو GPS) ورسم نقطة "أنت هنا" فوق الطبقتين السابقتين عند توفّرها.

**ملاحظة تقنية مهمة حول الأداء**: كل هذا يحدث **مرة واحدة فقط** عند فتح الشاشة. بناء شبكة الـ Graph (للحساب لاحقاً بقسم 6) يحدث أيضاً هنا، مرة واحدة، وتبقى محفوظة بالذاكرة طول فترة استخدام الزائر للتطبيق — لا حاجة لإعادة طلبها من الخادم أو إعادة بنائها مع كل عملية حساب مسار.

## 4. تحديد موقع الزائر — يدوياً وعبر GPS (بالتفصيل الكامل)

> هذا القسم يشرح بدقة تامة الخطوة الأهم بالنظام: كيف يعرف التطبيق "أين الزائر الآن؟". (نفس التفصيل المطلوب سابقاً، مدمج هنا ضمن العملية الكاملة).

### 4.1 الخيارين المتاحين دائماً للزائر
عند فتح الخريطة تظهر بوضوح زرّين: **[📍 حدد موقعي تلقائياً]** و **[✋ حدد موقعي يدوياً]**. الخيار اليدوي يبقى متاحاً دائماً كبديل مضمون، لأن GPS قد يفشل (داخل مبنى، إشارة ضعيفة، أو الزائر أصلاً خارج الحديقة).

### 4.2 المسار اليدوي — خطوة بخطوة

1. **استقبال لمسة الزائر**: نظام Flutter يعطي موضع اللمس بوحدة بكسل الشاشة، وهذا ليس نفسه بكسل الصورة الأصلية بسبب التكبير/التحريك الحالي داخل `InteractiveViewer`.
2. **التحويل لبكسل الصورة الأصلية**: نأخذ مصفوفة التحويل الحالية من `TransformationController`، نطبّق معكوسها على نقطة اللمس، فنحصل على الموضع بالنسبة للصورة كما هي قبل أي تكبير.
3. **تحويل لنسبة (Ratio)**: `ratio_x = نقطة/عرض_الصورة_المعروضة` و`ratio_y` بالمثل (قيم بين 0 و1، لضمان الاستقلالية عن حجم الشاشة).
4. **تحويل النسبة لبكسل الصورة الأصلية**: `original_x = ratio_x × 4516` و `original_y = ratio_y × 3374`.
5. **فحص الحدود**: لو النقطة خارج حدود الصورة بالكامل، تُجاهَل اللمسة بصمت.
6. **البحث عن أقرب عقدة**: مسح كل العقد الـ122 النشطة (`is_active=true`)، حساب المسافة الإقليدية لكل منها من `(original_x, original_y)`، واختيار الأقل:
   ```
   لكل node: distance = sqrt((node.x - original_x)² + (node.y - original_y)²)
   أقرب_عقدة = node بأقل distance
   ```
7. **فحص الحد الأقصى المسموح**: لو `أقرب المسافات > 250 بكسل` (قيمة تُضبط بالتجربة): تظهر رسالة *"هذا المكان بعيد عن أي ممر معروف. حاول الضغط بالقرب من أحد الممرات"*، ولا نحفظ شيئاً، ننتظر محاولة أخرى.
8. **التأكيد**: تظهر بطاقة سفلية: *"تم تحديد موقعك. هل هذا صحيح؟"* مع [نعم، استمر] و[إعادة التحديد]. عند الموافقة: `startNodeKey = أقرب_عقدة.node_key`.

### 4.3 المسار التلقائي (GPS) — خطوة بخطوة

**4.3.1 طلب الصلاحية:**
- **مُوافَق** → نستمر.
- **مرفوض** أو **مرفوض دائماً** أو **خدمة الموقع مغلقة بالجهاز** → رسالة فورية: *"لم نتمكن من تحديد موقعك تلقائياً. حدّد موقعك يدوياً للوصول إلى وجهتك"* + زر [حدد يدوياً] يرجع للقسم 4.2.

**4.3.2 طلب قراءة GPS بمهلة 10 ثوانٍ:**
- نجاح → نحصل على `(latitude, longitude, accuracy_meters)`.
- فشل/انتهاء المهلة → نفس رسالة الفشل أعلاه + [حدد يدوياً].

**4.3.3 تحويل GPS إلى بكسل عبر Delaunay Triangulation (الشرح الرياضي الكامل):**

- **التحضير (مرة واحدة فقط عند تحميل الخريطة)**: نأخذ نقاط المعايرة من لوحة التحكم (كل نقطة = `(lat, lng)` حقيقي + `(pixel_x, pixel_y)` مقابل، يُفضَّل 6 نقاط أو أكثر منتشرة بكل أركان الحديقة وليس فقط 4 زوايا، لأن أرض الحديقة الحقيقية نادراً ما تكون مستطيلة منتظمة). نطبّق عليها خوارزمية Delaunay Triangulation فتنتج شبكة من المثلثات الصغيرة المتجاورة تغطي كل مساحة الحديقة بدون فراغات أو تداخل.

- **عند كل قراءة GPS جديدة**: نبحث عن أي مثلث من هذه الشبكة تقع نقطة `(lat, lng)` الجديدة بداخله، عبر حساب **الإحداثيات الباريسنترية (Barycentric Coordinates)**: لمثلث برؤوس A، B، C ونقطة P، نحسب أوزاناً `(u, v, w)` بحيث `P = u·A + v·B + w·C` و`u+v+w=1`. لو الأوزان الثلاثة موجبة (بين 0 و1)، فالنقطة داخل هذا المثلث بالتحديد.

- **تطبيق نفس الأوزان على البكسل**: بعد إيجاد المثلث الصحيح، نطبّق نفس `(u, v, w)` على بكسلات رؤوس هذا المثلث:
  ```
  pixel_x = u × A.pixel_x + v × B.pixel_x + w × C.pixel_x
  pixel_y = u × A.pixel_y + v × B.pixel_y + w × C.pixel_y
  ```
  هذا هو موضع الزائر التقريبي على صورة الخريطة.

- **لو لم تقع النقطة بأي مثلث**: إشارة قوية أن الزائر خارج المنطقة المغطاة بالمعايرة — أي تقريباً خارج حدود الحديقة (تفصيل القرار النهائي بالنقطة التالية).

**4.3.4 التأكد الصريح من أن الزائر داخل حدود الحديقة (Geofencing):**

نُعرّف **مضلّعاً (Polygon)** صريحاً يمثّل محيط أرض الحديقة بالكامل (قائمة نقاط GPS تُدخَل من لوحة التحكم)، ونطبّق خوارزمية **Point-in-Polygon (Ray Casting)**:
```
عداد_التقاطعات = 0
لكل ضلع بالمضلّع (نقطتين متتاليتين):
    إذا خط أفقي وهمي من نقطة الزائر للخارج يتقاطع مع هذا الضلع:
        عداد_التقاطعات += 1
النتيجة: عداد فردي = الزائر "داخل"  /  عداد زوجي = الزائر "خارج"
```

**لو كانت النتيجة "خارج" (بعد 3 قراءات متتالية بنفس النتيجة، لتجنّب الوميض عند حافة الحدود — Hysteresis):**
> 🚫 **أنت لست داخل الحديقة حالياً**
> لا يمكننا تحديد موقعك تلقائياً بدقة. حدّد موقعك يدوياً على الخريطة للوصول إلى وجهتك.
> [حدد موقعي يدوياً]  [إغلاق]

زر [حدد موقعي يدوياً] ينقل الزائر مباشرة لتجربة القسم 4.2. لا نمنعه من استعراض التطبيق أو معلومات الحيوانات، فقط نمنع الاعتماد التلقائي على GPS لحساب المسار.

**لو `accuracy_meters > 50` حتى لو داخل المضلّع رياضياً**: تُعامَل كحالة غير موثوقة، رسالة مخفّفة: *"دقة موقعك الحالية ضعيفة. تأكد أنك بمنطقة مفتوحة، أو حدّد موقعك يدوياً"* + [إعادة المحاولة] [حدد يدوياً].

**4.3.5 تنقية القراءات (Smoothing) قبل العرض:**

- **المتوسط المتحرك (نبدأ بهذا)**: نحتفظ بآخر 5 قراءات بكسل، ونعرض متوسطها الحسابي البسيط. يقلل الارتجاف لكن يسبب تأخّراً بسيطاً مقبولاً لمشي بطيء.
- **مرشّح كالمان (تحسين لاحق لو احتجناه)**: يبني نموذج توقّع (موقع + سرعة)، ويدمج كل قراءة جديدة مع التوقّع بوزن يعتمد على `accuracy_meters` الفعلية لتلك القراءة (قراءة سيئة الدقة تُعطى وزناً أقل تلقائياً).

**4.3.6 عرض نقطة "أنت هنا" + دائرة نطاق الخطأ، وتحديثها باستمرار** (Stream قراءات كل 1-2 ثانية أو كل تحرّك 3 أمتار، مع حركة سلسة Animation بين الموضع القديم والجديد).

### 4.4 النتيجة الموحّدة من كل ما سبق
بغض النظر عن المسار (4.2 أو 4.3)، تنتهي العملية دائماً بمتغيّر واحد: **`startNodeKey`**. خطوة حساب المسار التالية لا تعرف ولا يهمها من أين أتت هذه القيمة.

## 6. حساب أفضل مسار (خوارزمية Dijkstra) — بالتفصيل الكامل مع كود

### 6.1 بناء الـGraph بالذاكرة (مرة واحدة عند تحميل الخريطة، قسم 3)

```dart
class GraphNode {
  final String key;
  final double x, y;
  GraphNode(this.key, this.x, this.y);
}

class GraphEdge {
  final String fromKey, toKey;
  final double distance;
  final List<List<double>> geometry; // كل نقاط الانحناء الحقيقي
  final bool isAccessible;
  GraphEdge(this.fromKey, this.toKey, this.distance, this.geometry, this.isAccessible);
}

class RouteGraph {
  Map<String, GraphNode> nodes = {};
  Map<String, List<GraphEdge>> adjacency = {}; // قائمة جيران كل عقدة

  void build(List<dynamic> nodesData, List<dynamic> edgesData) {
    for (var n in nodesData) {
      if (n['is_active'] == true) {
        nodes[n['node_key']] = GraphNode(n['node_key'], n['x'], n['y']);
      }
    }
    for (var e in edgesData) {
      if (e['is_active'] != true) continue;
      var edge = GraphEdge(e['from_node_key'], e['to_node_key'], e['distance_units'], e['geometry'], e['is_accessible']);
      adjacency.putIfAbsent(e['from_node_key'], () => []).add(edge);
      if (e['is_bidirectional'] == true) {
        // نضيف نسخة بالاتجاه المعاكس أيضاً للمرور بكلا الجهتين
        adjacency.putIfAbsent(e['to_node_key'], () => [])
          .add(GraphEdge(e['to_node_key'], e['from_node_key'], e['distance_units'], e['geometry'].reversed.toList(), e['is_accessible']));
      }
    }
  }
}
```

### 6.2 خوارزمية Dijkstra نفسها

```dart
class PathResult {
  final List<String> nodeSequence;     // تسلسل العقد من البداية للنهاية
  final List<GraphEdge> edgeSequence;  // الحواف المستخدمة بالترتيب (لرسم الخط لاحقاً)
  final double totalDistance;
  PathResult(this.nodeSequence, this.edgeSequence, this.totalDistance);
}

PathResult? findShortestPath(RouteGraph graph, String startKey, String endKey, {bool wheelchairOnly = false}) {
  Map<String, double> distances = { for (var k in graph.nodes.keys) k: double.infinity };
  Map<String, String?> previousNode = {};
  Map<String, GraphEdge?> previousEdge = {};
  distances[startKey] = 0;

  var unvisited = Set<String>.from(graph.nodes.keys);

  while (unvisited.isNotEmpty) {
    // اختيار العقدة الأقل مسافة من بين غير المُزارة
    String? current;
    double bestDist = double.infinity;
    for (var k in unvisited) {
      if (distances[k]! < bestDist) { bestDist = distances[k]!; current = k; }
    }
    if (current == null) break;          // لا يوجد مسار متصل بعد الآن
    if (current == endKey) break;         // وصلنا للوجهة

    unvisited.remove(current);

    for (var edge in graph.adjacency[current] ?? []) {
      if (wheelchairOnly && !edge.isAccessible) continue;   // استثناء الممرات غير المناسبة
      var newDist = distances[current]! + edge.distance;
      if (newDist < distances[edge.toKey]!) {
        distances[edge.toKey] = newDist;
        previousNode[edge.toKey] = current;
        previousEdge[edge.toKey] = edge;
      }
    }
  }

  if (distances[endKey] == double.infinity) return null;   // لا يوجد مسار ممكن أصلاً

  // إعادة بناء المسار رجوعاً من النهاية للبداية
  List<String> nodeSeq = [endKey];
  List<GraphEdge> edgeSeq = [];
  String cursor = endKey;
  while (cursor != startKey) {
    edgeSeq.insert(0, previousEdge[cursor]!);
    cursor = previousNode[cursor]!;
    nodeSeq.insert(0, cursor);
  }

  return PathResult(nodeSeq, edgeSeq, distances[endKey]!);
}
```

### 6.3 ملاحظات مهمة على الكود أعلاه
- **التعقيد الزمني**: بسيط جداً (`O(n²)` تقريباً)، لكنه أكثر من كافٍ لشبكة من 122 عقدة فقط — تنفيذ فوري (أقل من جزء من الثانية) حتى على هاتف متوسط الأداء. لا حاجة لتحسينات مثل Priority Queue أو A* إلا لو كبرت الشبكة لاحقاً بشكل كبير (آلاف العقد).
- **معامل `wheelchairOnly`**: مثال على كيف تُفعَّل ميزة "مسار صديق لذوي الإعاقة" بسهولة — فقط نتجاهل أي حافة `is_accessible=false` أثناء البحث عن الجيران.
- **التعامل مع "لا يوجد مسار"**: لو الشبكة غير متصلة لأي سبب (خطأ بالبيانات، أو كل الحواف المؤدية لمنطقة معينة معطّلة مؤقتاً)، الدالة تُرجع `null`، ويجب على الواجهة عرض رسالة: *"تعذّر إيجاد مسار لهذه الوجهة حالياً، قد يكون الممر مغلقاً للصيانة"*.

## 7. رسم المسار على الخريطة

1. من `PathResult.edgeSequence` (قائمة الحواف بالترتيب)، نأخذ حقل `geometry` لكل حافة (قائمة نقاط الانحناء الحقيقي، وليس فقط بداية ونهاية).
2. نُسلسل كل نقاط كل الحواف ببعضها بالترتيب الصحيح، فنحصل على قائمة نقاط واحدة طويلة تمثل المسار الكامل من البداية للنهاية بانحناءاته الحقيقية.
3. نحوّل كل نقطة (بكسل الصورة الأصلية) إلى موضعها الحالي على الشاشة (حسب التكبير/التحريك الحالي لـ`InteractiveViewer`)، ونرسمها كخط (`Polyline` أو `CustomPainter` برسم `Path` متصل) بلون مميّز (أحمر أو أزرق) فوق كل الطبقات السابقة.
4. **تحديث الرسم تلقائياً** كل مرة يكبّر/يحرّك الزائر الخريطة (لأن موضع الشاشة لكل نقطة يتغيّر، بينما البكسل الأصلي ثابت دائماً).
5. عرض بطاقة معلومات: المسافة الإجمالية (`PathResult.totalDistance` بالبكسل، تُحوَّل لأمتار حقيقية عبر نسبة معروفة من بيانات المعايرة: مثلاً "كل 100 بكسل = X متر حقيقي"، تُحسب من المسافة بين نقطتي معايرة معروفتين)، والوقت التقديري للمشي (`المسافة_بالأمتار ÷ 1.2 م/ثانية` تقريباً).

---

## 8. التنقل الحي وإعادة الحساب التلقائي (ميزة متقدمة اختيارية)

1. بعد عرض المسار، يستمر التطبيق باستقبال قراءات GPS الحية (نفس آلية القسم 4.3) ويحدّث نقطة "أنت هنا" باستمرار.
2. بكل قراءة جديدة: نحسب المسافة العمودية (Perpendicular Distance) من نقطة الزائر الحالية لأقرب نقطة على خط المسار المرسوم.
3. لو هذه المسافة تجاوزت حداً معيناً (مثلاً 30 متراً) لعدة قراءات متتالية: نعتبر الزائر "خرج عن المسار"، ونعيد استدعاء `findShortestPath` من جديد بنقطة بدايته الحالية (أقرب عقدة لموضعه الجديد) لنفس الوجهة، ونرسم المسار الجديد.
4. (تحسين إضافي) تنبيه نصي عند الاقتراب من عقدة فيها تغيير اتجاه واضح بالمسار (مقارنة زاوية الحافة الحالية بالحافة التالية).

### 9.2 قاعدة البيانات (الجداول الخمسة)

(تفصيل كل حقل بكل جدول مذكور بالقسم 2 أعلاه، لأن هذي الجداول تخزّن حرفياً نفس بنية GeoJSON بعد تفكيكها لصفوف علائقية).

### 9.3 سير عمل تحديث الخريطة بالكامل (خطوة بخطوة)
1. فريق الحديقة (أو مصمم) يفتح أداة `map-path-editor.html`، يرسم/يعدّل العقد والحواف والمعالم فوق صورة الخريطة الجديدة أو المحدّثة.
2. تصدير ملف GeoJSON من الأداة.
3. بلوحة التحكم: صفحة **"رفع نسخة خريطة جديدة"** → رفع صورة PNG + رفع ملف GeoJSON.
4. خادم Laravel يقرأ الملف، يتحقق من تطابق `metadata.image_width/height` مع الصورة المرفوعة، ثم يفكّك كل `feature` ويوزّعها على الجداول (نوع `map_path_node` → جدول العقد، وهكذا)، **مع تطبيق تصحيح محور Y إن لزم عند هذه النقطة بالضبط** (نقطة واحدة موحّدة للتحويل، لا تتكرر بأي مكان آخر بالنظام).
5. تُنشأ نسخة جديدة بجدول `maps` بحالة `is_active = false` (غير معروضة للزوار بعد).
6. صفحة **"معاينة"**: تعرض النسخة الجديدة فوق صورتها مباشرة بلوحة التحكم (نفس منطق الفحص البصري الذي استخدمناه سابقاً لفحص الملف يدوياً)، للتأكد البصري أن كل شيء بمكانه الصحيح قبل نشرها للزوار.
7. بعد التأكد: زر **"تفعيل هذي النسخة"** → تُصبح `is_active=true`، وتلقائياً تُعطَّل النسخة السابقة (`is_active=false`، تبقى محفوظة بقاعدة البيانات لا تُحذف، لإمكانية الرجوع لها لاحقاً عند الحاجة).

## 12. الأخطاء الشائعة ونقاط يجب الانتباه لها (خلاصة عملية)

1. **اتجاه محور Y**: يجب الاتفاق عليه من اليوم الأول وتطبيق أي تصحيح **بنقطة واحدة فقط** بالنظام (عند الاستيراد لقاعدة البيانات)، وعدم تكراره أو نسيانه بأي طبقة لاحقة.
2. **الخطوط المستقيمة بدل المتتبعة**: عند رسم أي حافة جديدة بالأداة، يجب التأكد أنها تتبع شكل الممشى الحقيقي بنقاط متعددة، لا خط مستقيم بنقطتين فقط، خصوصاً بالمناطق المزدحمة بالمباني/الأقفاص.
3. **اختبار ميداني حقيقي لـ GPS**: المعايرة الرياضية مهما كانت دقيقة تحتاج اختباراً فعلياً بالمشي داخل الحديقة، لأن دقة GPS الحقيقية تتأثر بعوامل لا يمكن التنبؤ بها بالمكتب (الأشجار الكثيفة، المباني، الطقس).
4. **العقد المنعزلة أو الشبكة غير المتصلة**: كل تعديل جديد بالأداة يجب أن يُفحص ببساطة: هل لا تزال كل عقدة بالشبكة قابلة للوصول من كل عقدة أخرى؟ (فحص اتصال بسيط Graph Connectivity كما طبّقناه سابقاً عند فحص الملف).
5. **عدم حذف البيانات القديمة نهائياً**: تعطيل (`is_active=false`) دائماً أفضل من الحذف الفعلي، لإمكانية الرجوع أو التحقيق بمشكلة لاحقاً.
